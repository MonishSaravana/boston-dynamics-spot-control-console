SCOPE · Spot control console

How SCOPE works

What happens inside the console when it drives Spot, maps the room, finds an object from a typed word, and walks to it. With the math, and pictures of each mechanism.

Evidence: written from the source code, the unit tests, and timings on the development laptop. Nothing here was measured on a physical Spot. Diagrams that illustrate an algorithm are computed with the same rules the code uses; their example inputs are made up.

01The whole system

SCOPE runs entirely on your laptop. A Python program, scope_web.py, serves the console page on 127.0.0.1 and does all the work. Spot never runs SCOPE code. It answers requests from Boston Dynamics' SDK, and only the Python program talks to it.

The desktop consoles (spot_control_gui.py for manual control, python -m scope.m5_console for targeting) reuse the same SpotSession and the same perception code, so everything below applies to them too.

02Walking to the chair, end to end

The main feature is "find this object and walk to it". It runs as two lanes that meet at the destination.

The rest of this guide follows those boxes: first how SCOPE talks to Spot and drives it, then frames and cameras, then the map, the search, the box, the destination, and GO.

03Talking to Spot

Spot exposes services over the network using gRPC, a protocol for calling functions on another computer. The Python SDK (bosdyn-client) wraps those calls.

ServiceUsed forWhere in the code
Authenticationusername and password for a session tokenrobot.authenticate
Time syncoffset between the laptop clock and Spot's clocktime_sync.wait_for_sync
Imagecamera and depth images, with calibration and posespot_live_source.py
Robot statejoint angles, body speed, standing or not, frame transforms_state_loop, robot_pose
Leaseexclusive permission to command the robotLeaseKeepAlive
Powermotors onrobot.power_on
Robot commandstand, velocity, posture, walk to a poserobot_command

Lease. Only one program can command Spot at a time. SCOPE takes the lease in Robot control and returns it on Disconnect or exit. Observe and Dry run never take it, so they cannot move the robot.

E-stop. Spot will not run its motors without an E-stop client checking in. SCOPE deliberately isn't one. The SDK's estop_nogui.py is, and pressing Space there cuts motor power. SCOPE's red STOP MOVEMENT button only sends zero velocity.

Time sync. Every image and state message carries Spot's timestamp. SCOPE converts "now" on the laptop into robot time and rejects anything older than 0.6 s. Without time sync, that check would compare two unrelated clocks.

04Driving, standing and posture

All of this is in SpotSession in spot_control_gui.py. A single worker thread sends every command, so two commands never overlap.

Velocity commands

While you hold keys, the worker sends a velocity command every 0.10 s:

forward = (W held) − (S held)        −1, 0 or 1
left    = (A held) − (D held)        −1, 0 or 1
scale   = max(1, √(forward² + left²))
vx = speed · forward / scale         m/s ahead
vy = speed · left    / scale         m/s to the robot's left

The scale term stops diagonals from being faster. At 0.20 m/s, W+A gives vx = vy = 0.141 m/s, which is still 0.20 m/s overall.

Each command carries an end time 0.35 s in the future. Spot drops it after that unless a newer one arrives. That's what makes a crash or a dropped Wi-Fi connection safe.

Stand, and what "armed" means

Stand sends a stand command, then SCOPE ignores the acknowledgement and polls robot state for up to 10 s. It sets armed only when all of these are true:

  • behavior state is STATE_STANDING,
  • the state sample is under 0.6 s old in robot time,
  • body speed is under 0.03 m/s and turning speed under 0.05 rad/s.

Keys, posture and GO stay locked until then. A second thread re-reads state every 0.5 s. If it goes stale or errors, the session un-arms and stops.

Body posture

Apply sends another stand command with body_height (0 to +0.10 m above Spot's normal standing height) and footprint_R_body = EulerZXY(roll, pitch), the body's tilt relative to its feet (±5°). Spot's controller decides how to move the legs, and it can limit the request.

05GO on the real robot

GO sends one SE2 trajectory point command: "go stand at x, y, facing yaw, in the odom frame". Spot's own walking controller plans the steps. The executor is scope/spot_navigation.py, and it has only been tested against a fake robot.

LimitValue
Max speed0.20 m/s forward, back and sideways
Max turn rate0.30 rad/s (about 17° per second)
Route length2.5 m, or GO is refused
Command lifetime0.75 s, renewed every cycle
Overall timeout15 s

Meanwhile the browser tab sends a heartbeat every 100 ms. If the server hears nothing for 0.30 s, because the tab was hidden, the window lost focus or the laptop slept, it stops the walk. Manual keys, posture and gestures are refused while GO is running.

06Coordinate frames

Every position in SCOPE says what it is measured from.

FrameMeaning
odomFixed to the room where Spot started tracking. Spot updates the body's position in it from its legs and IMU. Maps, targets and GO goals all use it.
bodyCenter of Spot's body: x forward, y left, z up.
cameraThe lens center: x right in the image, y down, z out of the lens.

A 4×4 transform holds a rotation R and a translation t, and moves a point with p_odom = R · p_camera + t. Transforms chain by multiplying. The robot's heading comes from its rotation matrix as yaw = atan2(R[1,0], R[0,0]). SCOPE rejects any matrix that isn't a true rotation, because a bad one would stretch or mirror the map.

odom drifts slightly as Spot walks, since it is added up step by step. Over a few meters this is small. SCOPE doesn't correct it.

07From a pixel to a 3D point

Spot's body has five stereo camera pairs. Each gives a grayscale fisheye image and a depth image. Spot can also re-project the depth into the camera's own view, under names like frontleft_depth_in_visual_frame.

u = fx · X / Z + cx          v = fy · Y / Z + cy        (3D → pixel)
X = (u − cx) · Z / fx        Y = (v − cy) · Z / fy      (pixel + depth → 3D)

Example: fx = 300, cx = 320, a pixel at u = 470 with depth 2.0 m gives X = 150 · 2.0 / 300 = 1.0 m to the right.

Fisheye lenses

Spot's lenses follow the Kannala-Brandt fisheye model, which adds four distortion numbers. The formulas above only hold after straightening the image, so pair_to_frame remaps both images to a pinhole view with OpenCV's fisheye functions. Color is blended between neighboring pixels. Depth is not: blending across an edge would invent a surface halfway between a chair and the wall behind it, so depth uses the nearest pixel.

Depth units and timing

Depth arrives as 16-bit integers with a depth_scale (raw units per meter), so meters = raw / depth_scale. A raw 0 means no reading and becomes NaN, so it can never pass as a surface at 0 m. Color and depth must be captured within 50 ms of each other, and both must be under 0.6 s old.

08What “alignment verified” means

It answers one question: does depth pixel (u, v) describe the same point in the room as color pixel (u, v)? Everything 3D depends on it, because SCOPE finds the object's pixels in the color image and then reads depth at exactly those pixels.

What the code checks

  • same image size for color and depth,
  • sensor positions within 3 cm, rotations nearly equal,
  • a valid depth scale, and matching fisheye calibration,
  • captured within 50 ms of each other.

What it can't check

Whether the robot's stored calibration is right, and whether you paired the right depth source with the camera. There is no ground truth to compare against, so ticking the box is you confirming you looked.

Suggested check on the robot
  1. Connect in Observe. Under Sources, acquire and display the camera and its _depth_in_visual_frame partner.
  2. Open Split view. Depth shows as grayscale: dark is near, white is about 5 m or farther.
  3. Put something with sharp edges about 1.5 m away, against a wall farther back.
  4. Its outline should sit in the same place in both images. Optionally, check one distance with a tape measure.
  5. If it lines up, select that pair in Sources, tick alignment verified, and apply.

Without it you still get cameras, manual drive and image-only search, but no map, no 3D target and no GO.

09Building the 3D map

The room is divided into 10 cm cubes called voxels (VoxelMap in scope/mapping.py). Each voxel keeps two counters: how many depth rays ended in it, and how many passed through it.

for every 3rd pixel with depth 0.15–5.0 m:
    p = back-project pixel, move to odom          (sections 6–7)
    hits[voxel(p)] += 1
    for s = 0.05, 0.10, … up to depth − 0.075 m:   (stop short of the surface)
        frees[voxel(camera + (p − camera) · s / depth)] += 1

state = OCCUPIED if hits > 0, else FREE if frees > 0, else UNKNOWN

NumPy's add.at applies all the increments in one call, so a frame takes milliseconds.

The top-down view

The map's size is set once, from the first good RGB-D frame: everything visible plus 0.4 m on each side, capped at 2 million voxels. Points outside that box are dropped. From the third frame on, SCOPE checks how many new points land within 18 cm of existing ones. Under 12% logs a warning, which usually means a pose or calibration problem.

10Finding an object from text

You type "chair". Two local AI models look at the current camera image (scope/open_vocab.py). Neither runs on a server: PyTorch runs them on your laptop, on an NVIDIA GPU if there is one, then Apple's GPU, then the CPU.

Grounding DINO Tiny proposes

An open-vocabulary detector finds boxes for any phrase, not a fixed class list. An image encoder (a Swin-Tiny transformer) turns the picture into features for each image patch. A text encoder (BERT) does the same for each word. Cross-attention layers let each side look at the other, so chair-like regions light up for "chair". The decoder outputs boxes, each with a similarity score to the phrase. SCOPE resizes the image to 512 px on the short side and keeps boxes scoring at least 0.45.

OWLv2 checks

OWLv2 is built on CLIP, a model trained so images and their captions land near each other as vectors. It gives every image patch a box and a vector. A box's score is how close its vector is to the vector for "chair". A Grounding DINO box survives only if an OWLv2 box scoring at least 0.15 overlaps it with IoU ≥ 0.3.

The phrase also gets a few synonyms first (sofa/couch, monitor/screen, backpack/bag and so on). Boxes with IoU ≥ 0.65 against a higher-scoring box are merged as duplicates. Scores are evidence, not probabilities, and two models can agree on the wrong thing.

Cutting out the pixels

A box includes floor and wall, so SCOPE runs OpenCV's GrabCut inside it. GrabCut fits one color model for "inside" and one for "outside", builds a graph where neighboring pixels with similar color are expensive to separate, and cuts the graph along the cheapest boundary. It repeats that 3 times. Masks under 24 pixels are rejected.

The search runs on a background worker that keeps at most one job waiting, and it repeats every 1.5 s while a phrase is active. The README reports about 1 s per search on the M4 test laptop.

11From a mask to a 3D object

project_object in scope/objects.py turns mask pixels into a box in meters.

keep pixels with depth 0.15–5 m       (need ≥ 12 of them, ≥ 25% of the mask)
m   = median(depth)
MAD = median(|depth − m|)
keep |depth − m| ≤ max(0.35 m, 4 · 1.4826 · MAD)
box = 2nd to 98th percentile of the 3D points, per axis

1.4826 · MAD estimates the standard deviation without being dragged by outliers, and the percentiles stop a few stray points from stretching the box. The box covers only surfaces the camera saw; the far side of the chair isn't in it.

One chair, many views

Each search on a new frame adds a fresh observation. scope/entities.py decides whether it is a known object or a new one by scoring every pair:

score = 0.20 · class agreement
      + 0.30 · exp(−½ · (center distance / object size / 0.45)²)
      + 0.25 · min(1, 3 · box IoU)
      + 0.25 · share of new points within 12 cm of the object's points

A pair is ruled out if the classes disagree, the centers are more than 0.85 object-sizes apart, the boxes are over 18 cm apart, nothing overlaps, or the score is under 0.43. The Hungarian algorithm then picks the best one-to-one pairing, so two observations can't both claim the same chair. Unmatched observations become new objects, named like chair_01. When an observation merges, the object's box becomes the union of both boxes, so it can grow but never shrinks.

12Following the object between searches

The detectors are too slow to run every frame, so scope/object_tracking.py moves the mask in between.

  1. Find up to 80 high-contrast corners inside the mask.
  2. Track them with pyramidal Lucas–Kanade optical flow: compare 21×21 pixel patches over four image sizes to find where each moved.
  3. Track back, and keep points that return within 1.5 px. At least 4 points and 35% must survive.
  4. Fit a shift, rotation and scale with RANSAC, which ignores outliers. Reject scale outside 0.8–1.25× or jumps over 40% of the image.
  5. Move the mask, then compare its color histogram with the original. If they differ too much (Bhattacharyya distance above 0.55), the track is lost.

A track counts as verified for 3 s after the last real detection. If the target's box moves more than 10 cm, your confirmation is dropped and you have to confirm again.

13Choosing where to stand

propose_destination in scope/live_interaction.py works on the flat top-down map.

c    = center of the target box
dir  = unit vector from c toward the robot
goal = c + dir · (half the box diagonal) + dir · 1.2 m
yaw  = direction from goal to c
route: samples every ~0.1 m from robot to goal, each needing a free disk
       of 0.42 m footprint + 0.15 m clearance; unknown counts as blocked

If the direct approach is blocked it tries ±30° and ±60°, then gives up with "DESTINATION BLOCKED or unknown". There is no path planner. A blocked straight line is a refusal, not a detour.

14Pointing at a target

Optional: enable human pose when connecting.

  1. Keypoint R-CNN finds people and 17 body joints in the image.
  2. Each joint is lifted to 3D using the median depth of a 5×5 patch, but only if the patch is consistent (MAD ≤ 12 cm), so a wrist in front of a wall doesn't take the wall's depth. Pixel and depth uncertainty become a 3D uncertainty ellipsoid through the projection's Jacobian.
  3. The arm direction is 75% forearm and 25% shoulder-to-wrist. A hanging or bent arm scores low. If no arm is clear, or both arms look equally plausible, it abstains.
  4. It draws 256 possible arm positions from those uncertainties and adds 3° to 24° of extra angle noise, depending on how complete the arm is.

15Gesture mode

Gesture mode runs Google's MediaPipe hand-gesture and body-pose models locally on the front-left camera (spot_gesture.py). It needs exactly one person and one hand, with the hand near one of that person's wrists, and a confidence of at least 0.85.

Distance comes from the torso: a patch between the shoulders and hips, shrunk 25% from each edge so it stays off the outline. SCOPE uses the nearest valid person pixel, including an outstretched hand, so any error makes it stop sooner. Each gesture command lives at most 0.15 s.

16The 3D robot model

The meshes come from the SDK checkout, spot-sdk/files/spot_base_urdf.zip. A URDF is an XML file listing the robot's rigid parts and the joints between them: where each joint sits, which axis it turns around, and its angle limits. In Measured mode the 12 joint angles come from Spot's telemetry, and the model only shows when the robot's URDF matches the SDK file to within 0.1 mm.

Why the zip is read at runtime

StepMeasured on this laptop

First model request: imports, parse meshes, build JSONabout 160 ms
Every later request (cached)about 0.001 ms
JSON sent to the page0.22 MB

Unzipping is not the slow part, and it happens once per server start. Committing the meshes would not make the console noticeably faster, and it would put Boston Dynamics' files into this project's history, which the repository's rules forbid until the SDK's redistribution terms are settled.

17The front panorama

About every 2 s, OpenCV's stitcher takes the front-left and front-right images (downsized to 640×420), finds distinctive points in both, matches them, estimates how the two cameras are rotated relative to each other, and blends them onto one surface. It doesn't use Spot's calibration, so plain walls can make it fail and straight lines can bend. Nothing else depends on it.

18Safety, layer by layer

STOP MOVEMENT clears held keys and gesture mode, invalidates the target approval, and sends zero velocity. It also bumps an epoch counter that every request carries, so anything sent before the Stop is rejected even if it was already queued. It is not an emergency stop. The class E-stop is.

19First run on the robot

  1. Start the class E-stop in its own Terminal and confirm that Space stops the robot.
  2. Run .venv/bin/python scope_web.py, open Connection, choose Robot control, and tick command authority.
  3. Power On, then Stand. Wait for "Standing confirmed".
  4. Drive briefly at 0.20 m/s. Release and check it stops. Click outside the window while holding W and check it stops.
  5. In Sources, pair the front-left camera with frontleft_depth_in_visual_frame, do the alignment check, tick the box and apply. Watch the World map fill in.
  6. Put a chair 2.5–3 m ahead in open space. Search chair, pick it, and confirm.
  7. Check the destination: about 1.2 m in front of the chair, facing it, with a clear route.
  8. Hand on the E-stop, press GO. On a later try, press STOP MOVEMENT mid-walk to confirm it halts.

20Limits that matter on a real robot

Found while reading the code. None has been measured on Spot.

  • The map doesn't grow. Its bounds come from the first RGB-D frame plus 0.4 m. Routes outside it count as blocked. Reconnecting rebuilds it.
  • Occupied never clears. A person walking past stays on the map until it is rebuilt, and can block later routes.
  • The obstacle slice assumes z = 0 is the floor. If odom's zero sits elsewhere on your robot, the 0.25–1.55 m band is at the wrong height. Check whether low furniture shows as occupied. Anything under 25 cm is ignored by design.
  • Straight lines only. No path planning. Spot's built-in obstacle avoidance may also act, but SCOPE doesn't rely on or check it.
  • Grayscale cameras. The detectors and GrabCut work best in color, so "red chair" can't be verified and masks may be weaker.
  • Boxes only grow. A moved object can end up with a box covering both spots. A move over 10 cm drops your confirmation.
  • Odometry drift builds up over long walks.
  • Text search needs PyTorch and transformers, which requirements-console.txt doesn't install. Run pip install -e '.[perception]' on a fresh setup.

21Glossary

gRPC
The network protocol Spot's SDK uses to call robot services.
Lease
Exclusive permission to command Spot. One program holds it at a time.
E-stop
The real emergency stop, run as a separate SDK program.
odom
The room-fixed frame Spot tracks with its legs and IMU.
SE2
A flat pose: x, y and heading.
Transform
A rotation plus a translation that moves points between frames.
Intrinsics
fx, fy, cx, cy: how the lens maps 3D points to pixels.
Aligned depth
Depth re-projected so each pixel matches the same pixel in the color image.
Voxel
A 10 cm cube of the 3D map.
Ray casting
Walking along each depth ray to mark the space before the surface as free.
Open-vocabulary detector
A model that finds boxes for any phrase.
IoU
Box overlap: shared area divided by combined area.
GrabCut
Color-based cutout inside a box using a graph cut.
MAD
Median absolute deviation, a spread measure that ignores outliers.
Hungarian algorithm
Finds the best one-to-one pairing between two lists.
Optical flow
Estimating how image points moved between frames.
RANSAC
Fitting a model while ignoring outliers, by trying random subsets.
Forward / inverse kinematics
Joint angles to foot position, and back.
URDF
XML description of a robot's parts and joints.
